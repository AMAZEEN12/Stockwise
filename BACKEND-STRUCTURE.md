# Backend folder structure (the shared template)

Every backend engineer uses this layout. It is the layout already in the Stockwise repository (`AGENTS.md` → Architecture), written down so a new package is never a guess. Names of owners are the area names from `sdlc/plan.md`; change them here if people are reassigned.

├── service/
│   ├── pom.xml  mvnw  Dockerfile  .dockerignore                                                [Delivery and evidence]
│   └── src/
│       ├── main/java/ng/tesa/stockwise/
│       │   ├── StockwiseApplication.java                                                       [Delivery and evidence]
│       │   ├── config/        CorsConfig, SecurityConfig, ProblemSecurityHandlers, RequestIdFilter, AppProperties (done)
│       │   ├── web/           RootController: "/" and "/api/v1/health" (done)                  [Delivery and evidence]
│       │   ├── common/        Page, Problem, ErrorCode, ProblemHandler, NotFoundException (done); Idempotency to come
│       │   ├── db/            MigrationUndo (done): the undo runner                            [Data and rules]
│       │   ├── auth/          AuthController, TokenService, UserRepository, CurrentUser, Role (done)  [API and access]
│       │   ├── product/       Product, ProductRepository, StockState, ProductController (done)
│       │   ├── customer/      Customer, CustomerRepository, CustomerController (done)
│       │   ├── sale/          SaleService, SaleRepository, NewSale, RecordedSale, exceptions, SaleController (done)

│           └── db/

## Adding a new feature package (the recipe)
1. Add the path to `contract/openapi.yaml` first, and a dated, two-engineer line in `decisions.md` §3 (CI blocks a contract change without it).
2. If it needs tables: new `V<n+1>__name.sql` **and** `db/rollback/U<n+1>__name.sql`. Never edit an applied `V<n>` (CI blocks it).
3. Create `ng/tesa/stockwise/<feature>/` with: a record per row type, `<Feature>Repository` (plain SQL via `JdbcClient`, money as `long` kobo), `<Feature>Service` (`@Transactional`, guards in SQL `UPDATE … WHERE …`), `<Feature>Exceptions`, then `<Feature>Controller` (API owner). Agree the service method signature in the PR description before the controller is written.
4. Tests in the same package under `src/test`: `<Feature>IT` for each rule. Each rule needs a test that fails when the rule is removed; log it in `docs/rule-removal-log.md`.
5. Anything that records money or stock takes an `Idempotency-Key`.
6. Run `cd service && ./mvnw verify` before opening the PR.

## What is populated (2026-10-25)
- **Data and rules:** `db/`, `sale/`, `product/`, `customer/`, `common/Page`, migrations V1-V3 with undo scripts, the Monday seed and its generator, the concurrency evidence logs.
- **API and access** (built on `feat/backend-api` for Nnaemeka Chukwuma as help outside his area, for Isaac Bassey to review): `auth/`, `config/`, `common/` problem handling, `web/RootController`, and every `*Controller` for the v0.1.0 paths.
- **Delivery and evidence:** workflows, guard scripts, smoke and load scripts, docker-compose, Dockerfile, runbooks (from this template).
- **Tests:** `cd service && ./mvnw verify` gives **88 tests green** (2026-10-25). They are in packages that mirror `main` (`config/CorsIT`, `config/MoneyJsonIT`, `web/MondayJourneyIT`, `auth/AuthorizationIT`, ...).
- **Not started:** `restock/`, `reversal/`, `history/`, `dashboard/` (each has a `package-info.java`).
